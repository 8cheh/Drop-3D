# 同日第一轮：桌面端从评估到可运行

## 目标

把库已经做完的部分封装成能在 Windows 上双击运行的图形界面，用于内部测试。
界面要与库解耦、可打包、可测试。先评估再动手。

## 做了什么

分支 `feat/desktop-gui`。新增 `desktop/`、`tests/test_desktop_api.py`、
`tests/test_public_api.py`、`docs/decisions/0003-desktop-gui.md`、
`docs/guide/desktop-app.md`。

- **技术路线先做可运行原型再定案**，而不是先写方案。原型验证了四件事：
  pywebview 6.2.1 + Edge WebView2 渲染毛玻璃、JS↔Python 桥调用真实 `drop3d`、
  PyInstaller 冻结成功、冻结后的 exe 脱离 Python 环境算出 γ。
- **界面**：`pywebview` + WebView2，原生 HTML/CSS/JS，无框架无构建步骤。
  毛玻璃是 CSS 的 `backdrop-filter`，壁纸是它的前提而不是装饰。
  八个页面覆盖五条工作流加实验设计，中英双语可切换。
- **桥接**：`api.py` 是一个纯对象，不 import `webview`，因此整套桥接能在
  无显示器的 CI 上测试。所有方法返回字典、不抛异常。
- **打包**：PyInstaller `--onedir`，产物 **125.7 MB / 395 个文件**（干净 venv）。
  构建脚本默认先跑测试再打包。

## 结果

- **333 项测试通过**（原有 282 + 新增 51），用时 9 分 24 秒。
- `ruff check src tests desktop` 干净。
- 打包产物 125.7 MB；冻结 exe 独立运行，合成悬滴链路算出 **γ = 75.53 mN/m**，耗时 1.75 s。
- 用脚本驱动真实界面走完 14 个步骤（每页翻页 + 点按钮），**零 JS 错误**。
  界面里跑出的 γ = 75.812 mN/m，与 Python 侧一致。
- 设备环境：Python 3.12.2，numpy 2.2.6，scipy 1.15.2，显示器 3840×2160 @150%。

## 遇到的问题

这一轮几乎所有时间花在这五个坑上。**前四个都是「我想错了」而不是「库有 bug」**。

### 1. 打包带上了整台机器（932 MB → 126 MB）

第一次打包用的是 `--system-site-packages` 的 venv，PyInstaller 把整机
site-packages 全收了：**932 MB**，含 torch、OpenCV、transformers、jieba、ray。
本应用一个都不 import。换成干净 venv 后是 125.7 MB。

→ 构建脚本自己建 venv，绝不共享。

### 2. 依赖版本会改变产品数字（75.81 → 75.53 mN/m）

干净 venv 装到了 numpy 2.5.3 / scipy 1.18.1，同一个合成测量的 γ 从
**75.81 变成 75.53 mN/m，差 0.37%**。而库的 282 项测试是在 numpy 2.2.6 /
scipy 1.15.2 上验证的。

→ `requirements-desktop.txt` 用 `==` 钉死。会悄悄改变数字的构建不算可复现。

### 3. 窗口geometry：我按错误的屏幕尺寸算，而 pywebview 的单位又不一致

现象：窗口跑到屏幕右边外面，尺寸也不对。

定位过程比结论值钱：

- 先用 PowerShell 量，得到「屏幕 2560×1440、窗口 1240×840」；
- 但同一台机器上 `GetDpiForWindow` 返回 144（150% 缩放），
  而 `GetSystemMetrics(0)` 在**不感知 DPI 的 PowerShell 进程里**返回 2560——
  真实物理分辨率是 **3840×2160**。我的测量工具本身在骗我。
- 换成 DPI 感知的进程再量：屏幕 3840×2160，而 pywebview 把请求的 `x`/`y`
  乘了约 2.0（它用虚拟化的逻辑屏幕算位置），却把 `width`/`height` 按物理像素 1:1 处理。
  两套单位混在一起，所以「居中」居中不了。

→ 结论：不要跟工具包的单位约定搏斗。自己量真实的 work area 和缩放，
用 `SetWindowPos` 按物理像素放置；窗口先隐藏，等定位落实后再显示。
另外工具包会在启动序列里再应用一次自己的 geometry，所以定位要补一次。

**教训**：在不感知 DPI 的进程里截图和量窗口，拿到的是虚拟化后的坐标和降采样的像素。
这一轮前期的所有截图都是 2560×1440（真实 3840×2160），我据此做过两次错误的推断。

### 4. 原生亚克力把窗口变透明了

`DWMWA_SYSTEMBACKDROP_TYPE=3` + `DwmExtendFrameIntoClientArea(-1,-1,-1,-1)`
确实生效了，但整个 WebView2 表面与桌面合成，界面在花哨背景前不可读。
CSS 毛玻璃本身是够的。

→ 原生背景改成 `--acrylic` 显式开启，默认关闭。

### 5. 三个只在前端才暴露的 bug（都不抛异常，只是「没有内容」）

- **`bridge()` 给零参数方法传了 `{}`。** Python 侧是
  `TypeError: app_info() takes 1 positional argument but 2 were given`，
  到了 JavaScript 是 promise 被拒。表现是「模块地图卡片空的」——
  看起来像数据没准备好，不像参数传错。**带 payload 的方法全都正常，所以更难发现。**
- **序列化只走 dataclass 字段会丢属性。** `ValidityReport.error_codes`、
  `DynamicsReport.verdict`、`EllipseFit.aspect` 都是 property。
  只走字段会得到一个没有判决的闸门报告。已改为一并带上公开属性。
- **`remedyList`/`libraryNote` 没有解构。** `remedyList is not defined`——
  这个反而是好事：驱动脚本一跑就抛了。前两个不抛，是「安静的空白」。

→ 这三条都写成了回归测试，写在前端之前。

### 6. 顺带发现库里的一个真 bug

`drop3d.__all__` 里列着 `footprint_from_contact_line`，
但 `src/drop3d/__init__.py` 从未 import 它：

```
>>> from drop3d import *
AttributeError: module 'drop3d' has no attribute 'footprint_from_contact_line'
```

函数本身没问题，从 `drop3d.dynamics` 单独 import 也能用——
所以整个绿色测试套件都发现不了它。已修，并加了 `tests/test_public_api.py`
守 `__all__` 与实际可导入名的一致性。

### 7. 把「未验证」写进界面的方式

调研结论是「无真实实验数据」是当前最大阻塞项，而合成图是测试夹具。
但这是面向使用者的软件，不需要在每个角落贴免责声明。做法是：

- 合成数据在数据出处的位置带一个标记；
- 每个页面都能一键生成合成数据，让整条链路可以被完整体验；
- 库自己的英文消息**原样引用并标注「库原始输出」**，不翻译——
  库的消息是写给看 traceback 的人看的，改写成中文等于替库说话。
