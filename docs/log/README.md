## 为什么要写

1. **给未来的自己**：三天后你会忘记为什么选了 A 而不是 B。
2. **给队友**：`RainMean624`、`8cheh` 不需要读代码就能知道进展到哪、卡在哪。
3. **给评委/答辩**：完整的研发过程记录本身就是成果的一部分，而且事后补不出来。

## 格式

```markdown
# YYYY-MM-DD

## 本日轮次索引      ← 一天多轮时加，带锚点

# 同日第 N 轮：<一句话说清这一轮干什么>

## 目标
这一轮打算完成什么

## 做了什么
- 具体动作，带文件路径与提交号

## 结果
- 可验证的结论。有数字就给数字，没有就写「未验证」

## 遇到的问题
- 现象 → 定位过程 → 结论。**失败的尝试也要写**，这是最有价值的部分

## 下一步
- 从哪继续
```

## 写作要求

- **区分「已验证」与「推测」**。验证过的写结论，没验证的写「推测，未验证」。
- **拒绝空洞的进度描述**。「推进了 XX 模块」没有信息量；「XX 模块的 P_s 计算在
  合成数据上与精确解差 2%，阈值定在 0.15」才有。
- **数字优先**。任何「效果不错」「基本可用」都应该换成数字，或者标注为未验证。
- **推翻旧结论时，旧记载原样保留**，另起一节写明更正。
  一条带实测表格、带测试、看起来很严谨的「已知局限」也可能整个是错的，
  **这个记录本身就是产出**——删掉它等于抹掉最贵的教训。
- **写清楚哪些坑是「我想错了」而不是「库有 bug」**。
  前者对读者更有用，因为它会重复发生。
